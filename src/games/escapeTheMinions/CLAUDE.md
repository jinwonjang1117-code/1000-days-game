# Co-op Roguelike — Project Context

This file is persistent context for Claude Code. Read this before starting any task on the co-op roguelike. This game shares a repo with an existing platformer (Hungry Monster clone) — do not modify the platformer's files unless a task explicitly says to touch the shared main menu.

**Full design detail lives in [DESIGN.md](DESIGN.md)** (same directory) — the design doc, with the complete role/item/enemy/combo tables, run structure, and sprite checklist. This file is a condensed summary plus the engineering-specific decisions DESIGN.md doesn't cover (networking internals, build phases, working conventions). When the two disagree, DESIGN.md is the source of truth for game design; this file is the source of truth for how it's actually built so far.

**Core design tenet (DESIGN.md, top of file — read it before touching any role/strong/boost item work): roles, strong items, and boost items must compose by default.** They all modify the same underlying default-attack projectile (or, for Laser/Bomb, replace its shape) — Ice's freeze should still get multiplied by Multi Shot, still steer with Homing, still scale with a damage boost, not exist in its own silo. Every new item in these three tiers gets checked against this before it ships; any deliberate exception (Buddy's fixed non-scaling damage) must be called out explicitly, not left as an accident.

## What this game is

A 2-player online co-op roguelike, shared-screen/shared-room (both players always in the same room together, not separate screens), inspired by The Binding of Isaac. One player hosts a room and shares a short room code; the other joins with that code. Runs are randomized and replayable: randomized item drops, randomized room enemy composition, seven selectable "roles" (elements) with mechanical synergies between them. Also playable single-player (`PlayScene.ts`) — single-player has always been "the same host-authoritative simulation with no joiner," so it's not a separate mode built twice; see the `GameSimulation` build-status entry below for the split.

## Architecture decisions (settled — don't relitigate without asking)

- **Stack:** Vite + TypeScript + Phaser 3, same repo as the platformer, routed to via the existing main menu scene.
- **Physics:** Arcade Physics, gravity disabled (`{ x: 0, y: 0 }`) — this is a top-down game, not a platformer. 8-directional movement via velocity, with diagonal movement normalized so it isn't faster than cardinal movement.
- **Camera:** Static per room. The camera never scrolls or follows a player within a room — it only cuts/transitions between rooms. This is a deliberate Isaac-style choice and also sidesteps multiplayer camera-follow conflicts.
- **Networking:** PeerJS (WebRTC), host-authoritative. The host's game instance is the source of truth: it simulates both players, all enemies, and resolves all hits/collisions, and broadcasts authoritative state. The joiner sends only input (movement direction, attack triggers) to the host — the joiner never simulates their own movement locally; they render based on interpolated state received from the host, never local prediction.
- **Room code flow:** Host generates a short alphanumeric PeerJS id, displays it; joiner enters it to connect. Handle failed/nonexistent codes with a visible error, not a silent hang.
- **Pause:** Either player can pause (e.g. Esc) — pauses for both, opens a menu on both screens. Matters more than it sounds: single-sitting runs of 70-90 rooms (see Run Structure) need a real pause. Built — see the build-status entry below. Host-authoritative like everything else: the joiner's Esc is a request (`PauseToggleMessage`), only the host actually flips `isPaused` and freezes the world (`this.physics.pause()`), same as the platformer's `GameScene.ts` already does for its own freeze moments.
- Networking is layered UNDER regular gameplay code, not bolted on after. Player movement, attacks, and room logic should be written so they don't care whether input came from a local keypress or a forwarded network message — same input-handling code path either way.

## Lives & death (settled — DESIGN.md §3)

No HP pool — players have a direct life count, any hit removes exactly one life (no damage variance), with ~1-1.5s of post-hit invincibility (visual flicker) so overlapping hits can't delete multiple lives at once. Lives are per-player, not shared. Starting lives: 5. Running out takes you out for the rest of the current level (input ignored, sprite grayed out); you respawn at the start of the next level with a **fixed 3 lives** (not the starting 5, not inherited from your teammate — this was previously TBD, now settled). If both players are out within the same level, the run ends. Rare life-item drops on room-clear grant +1, capped at max lives.

**Heart containers** (built — see build-status entry below): a max-lives cap alongside the current count, starting at 5. Grows two ways — passively, +1 every 2 levels (a deliberate departure from how Isaac does health scaling, which is 100% item-driven with no depth-based growth), and via the Heart Container strong item (+1 max, fills the new capacity immediately). Life items top up toward the cap rather than being unbounded.

- `src/games/escapeTheMinions/gameplay/lives.ts` — host-only pure state (`LifeState`, `applyHit`, `respawnForNextLevel`), consumed by `entities/Player.ts`. The joiner never runs this, only renders what the host broadcasts.
- `src/games/escapeTheMinions/gameplay/flicker.ts` — reusable invincibility-flicker visual, driven locally on each client (not synced frame-by-frame — only the `isInvincible` boolean travels over the network).
- `respawnForNextLevel` is wired up — see the build-status entry below. `GameSimulation.startLevel()` (called on every level transition, including the boss-hole one) is the real level-clear trigger this was originally waiting on.
- **Life display** (built — see build-status entry below): a heart-icon row (filled = red heart, empty = white heart, one per max-life slot), not the old floating "❤️ N" text above the player square. Own hearts render top-left (larger); your partner's render smaller, top-right above the minimap. Solo has no partner row.

## Attack system (settled — DESIGN.md §4)

Two distinct attack-input shapes, branching by equipped role (was three — Bomb's hold-to-charge concept was simplified away before it was built, see the Role system entry below):

| Input pattern | Roles |
|---|---|
| Space → fire projectile toward the direction you're facing | Ice, Glue, Poison, Electric, Gravity, Bomb |
| **Hold** Space → continuous beam while held, hits all enemies in the line each tick (settled, was "tap for an instant single beam") | Laser |

Every character has this baseline "default attack" (tears-style) before any role is equipped — a role changes *what the attack does and how it's fired*, not whether an attack exists. Aim is keyboard-driven (whichever way you're currently moving, or last moved) — no mouse involved anywhere in this game; settled, previously "click → fire toward cursor." Laser's beam thickness scales with the same size stat (`potatoSizeMultiplier`) that scales projectile radius for every other attack shape — one stat means "how big is my attack," regardless of shape.

Only the first row (fire the default projectile) is built so far — see the build-status entries below, including the room-clear items that now modify this same default projectile (damage/speed/range/size multipliers, Multi Shot, Multi Direction, Piercing, Homing) and its actual location today (`simulation/GameSimulation.ts`'s `tryFirePlayer`, not `CoopPlayScene.ts` — see the `GameSimulation` extraction entry). Laser is the only role still waiting on this — `src/games/escapeTheMinions/gameplay/attack.ts` + `entities/Projectile.ts` are where its eventual branch point will go. **Retired gap**: `tryFirePlayer`'s single `firing: boolean` was once flagged as too thin for Bomb's charge duration — moot now that Bomb doesn't charge. Laser only ever needed held/not-held, which `firing: boolean` already covers, so no input-model rework is actually needed for the one role left.

## The seven roles (settled — DESIGN.md §5)

Ice, Glue, Poison, Electric, Gravity, Laser, Bomb. Fire was considered and removed. Full effect/attack-shape/notes table in DESIGN.md — the one non-obvious one: **Bomb costs a full life** (not partial damage) if the player or teammate is caught in the blast, and only Electric can detonate a live bomb early.

### Role acquisition (settled — supersedes the old free-pick/shop rules, **design only — not yet built**)

Roles are **found, not chosen at run start** — a single-equip item sourced from golden-room/boss-room drops, same as strong items (see Item system below), but its own mutually-exclusive category: picking up a new role **replaces** whichever one you have, no stacking, no migration/refund for anything that specialized around the old one (intentional — deliberate cost of a role change). **No free starting pick, no guaranteed early role** — playing the early game on nothing but the default attack is an accepted, normal state, not a gap to fill. The shop-based role-change path is retired along with the shop system it depended on.

## Synergy / combo system (settled — DESIGN.md §6)

Status effects are shared world-state — either player's ability can trigger a combo off a status the *other* player applied, not just their own. A handful of marquee combos are designed (see DESIGN.md table, e.g. Ice+Electric = shatter, Gravity+Laser = cluster-then-sweep, Electric+Bomb = early detonation — the **only** role allowed to interact with Bomb's fuse). Not all 21 role pairs need a bespoke effect — most just fall back to "naturally synergistic," and that's fine.

## Item system (settled — DESIGN.md §7)

- **Default attack** — baseline, always present, not randomized.
- **Boost items** — role-agnostic stat ups (attack speed, move speed, damage, etc.) plus role-specific modifiers (e.g. "+15% freeze chance") in the same tier. Regular room-clear reward. Role-agnostic half built — see build status below; role-specific modifiers still wait on a follow-up (the 5 built roles' base tuning lives in `gameplay/roles.ts` instead for now, not per-pickup boost items yet).
- **Holdable item** — a single equip slot, not a stacking collection. A new pickup auto-swaps and drops the old one on the ground (teammate can grab the discard). Each role has one signature holdable (DESIGN.md table); several universal/co-op holdables also compete for the same slot (self-immunity, teammate-immunity, Second Wind, etc.). Not built — waits on Stage 9.
- **Life items** — rare, unscheduled room-clear drop, +1 life, capped at max lives. Built, cap included — see build status below. `GameSimulation.handleItemPickup` refuses the touch entirely (no destroy, no effect, no reveal text — silent no-op, same treatment as a keyless golden-room door) when the specific touching player is already at max lives, so it stays on the ground for later/a teammate instead of being wasted.
- **Strong items** (built: Multi Shot, Piercing, Homing, Multi Direction, Heart Container, Heavy Shot, Buddy, Orbiting Shield — see build status below) — a stackable pool sourced only from golden-room/boss-room drops, never the regular pool, and drawn 2-at-a-time from those rooms (built). Visually identified, not mystery — an earned reward, not a grab-bag roll. `ItemDefinition` has a `weight` field (mirrors the regular pool's) and a `unique` flag (built, but no current item sets it — groundwork for a future one-per-run item) for the handful that should cap at one per run instead of stacking freely.
- **Role items** (built: Ice/Glue/Poison/Electric/Gravity — see build status below) — define/change a player's role (see "Role acquisition" above). Sourced the same way as strong items (golden/boss/Angel rooms), joining their existing combined pool as a third category rather than a separate roll. Laser/Bomb role items withheld from every pool until their own follow-up stage.
- **Devil's Room items** (design only, not yet built) — exclusive to the Devil's Room (see build status below), never found elsewhere. Real risk/reward, usually a permanent heart-container cost for an outsized payoff.
- **Golden room** — one per level, no enemies, 2 guaranteed distinct items, now drawn from strong + boost + role items combined. See the build-status entry below.
- **Devil's Room** (design only, not yet built) — see build status below.

## Run structure (settled — DESIGN.md §8, §10)

10 levels, 7-13 rooms each, mini-boss ending levels 1-9, final boss (with role-favoring phases) on level 10 with no regular rooms. One Golden Room per level (built); a Devil's Room on a no-hit boss clear (design only, not yet built) — both DESIGN.md §9. Role items no longer have scheduled drops — purely golden/boss-room-sourced now, same as strong items. Five enemy archetypes (Swarmer, Tank, Chaser, Ranged shooter, Splitter) introduced on a schedule across levels 1-9. Room archetype mixing ramps up with floor depth (settled, implemented in `rooms/floorGenerator.ts`): single-archetype only below level 4, then a ramping chance to mix 2 archetypes from level 4, plus a smaller chance to mix 3 from level 8. Single-sitting only — no save/resume across sessions.

## Working conventions

- Before any multi-file change, outline the plan (files touched, key types/interfaces introduced) and wait for confirmation before implementing.
- When touching the networking layer or physics/collision math, flag it explicitly in your summary — these are the areas most worth a careful diff review.
- If a task would require guessing at how the existing main menu, the platformer's code, or an earlier phase's implementation actually works, inspect the relevant files first rather than assuming.
